Architecture générale

Trois processus, deux réseaux Docker. Le navigateur ne parle jamais à la base ; il parle au frontend Next.js et, pour tout ce qui est dynamique, directement à l'API Express sur le port 4000.

Qui fait quoi

frontend

Rend les pages, gère l'état d'interface et la carte. Il ne connaît pas la base : toute donnée passe par lib/api.ts, qui appelle l'API Express. Les pages serveur utilisent BACKEND_URL (nom de service Docker), le navigateur utilise NEXT_PUBLIC_API_URL.

backend

Seul à écrire en base. Il porte l'authentification (Better Auth monté sur /api/auth/*), la validation Zod, les règles de modération, l'enrichissement Sirene, l'envoi d'e-mails et la maintenance quotidienne (archivage des offres, purge des comptes inactifs).

db

PostgreSQL 16. Le schéma vit dans src/db/schema.ts ; les migrations SQL sont générées par drizzle-kit dans apps/backend/drizzle/ et rejouées au démarrage du conteneur backend.

Les quatre couches côté client

app/ — les écrans

layout.tsx installe les polices Manrope, le lien d'évitement, le fournisseur CGU, le contexte des candidatures et le cadre AppFrame. Chaque page exporte son metadata.

components/ — le métier

Un composant par bloc fonctionnel : map-explorer, job-list, job-details, applications-table, auth-modal… Ils reçoivent des données déjà typées et ne font pas d'appel réseau brut.

components/ui/ — les primitives

Boutons, dialogues, onglets, tableaux issus de shadcn/ui. Générés via components.json, style « new-york », alias @/components. On les modifie sur place, ils font partie du dépôt.

lib/ — le pont vers l'API

api.ts concentre tous les appels HTTP et convertit les lignes de l'API en types d'affichage (toJob, toCompanyPin). auth-client.ts expose la session Better Auth.

Deux bases d'URL, une seule raison

Un composant serveur tourne dans le réseau Docker : il doit viser http://backend:4000. Le navigateur, lui, ne connaît que http://localhost:4000. D'où ce sélecteur, à réutiliser pour toute lecture faite côté serveur :

apps/frontend/lib/api.ts
function apiBase(): string {
    if (typeof window === "undefined" && process.env.BACKEND_URL) {
        return process.env.BACKEND_URL;
    }
    return API_URL; // NEXT_PUBLIC_API_URL, validée dans lib/env.ts
}

Backend — Express

Un découpage strict en cinq fichiers par ressource : la route déclare l'URL, le middleware garde la porte, le controller décide, Zod valide, Drizzle écrit. Aucune requête SQL n'est écrite ailleurs que dans un controller.

Les fichiers d'une ressource

FichierResponsabilitéCe qu'on n'y met pas
routes/x.routes.tsVerbes, chemins, middlewares, blocs @openapiAucune logique
controllers/x.controller.tsDroits, validation, requêtes Drizzle, réponsePas de définition d'URL
schemas/x.schema.tsSchémas Zod postX / patchXPas d'accès base
db/schema.tsTables, contraintes, index, relationsPas de requêtes
routes/index.tsMontage de la ressource sous son préfixe—

Trois outils que tout controller utilise

  • getCurrentUser(req) — recharge l'utilisateur en base et refuse les comptes suspendus ou bannis, ainsi que ceux dont l'entreprise l'est. À préférer systématiquement à req.user.
  • getOptionalUser(req) — même chose sur une route publique, mais renvoie null au lieu d'échouer : c'est ce qui permet à un administrateur de voir ce que le public ne voit plus.
  • isUniqueViolation(error) — détecte le code PostgreSQL 23505 et permet de répondre 409 plutôt que 500 sur une contrainte d'unicité.
Convention d'imports

Le backend est en ESM nodenext avec allowImportingTsExtensions et rewriteRelativeImportExtensions. Les imports relatifs portent donc l'extension .ts : import {db} from "../db/index.ts";. Omettre l'extension casse l'exécution sous tsx.

Deux politiques de suppression, choisies volontairement

cascade quand la ligne n'a aucun sens sans son parent (une candidature sans offre, une compétence sans profil). set null quand la disparition du parent ne doit pas emporter l'enfant : supprimer une adresse ne supprime pas l'entreprise, supprimer une entreprise ne supprime pas le compte de son employeur.

Modération : des colonnes plutôt qu'une suppression

users et companies portent suspended_at, banned_at et moderation_reason. Une offre disparaît de la diffusion publique dès que son entreprise ou l'employeur qui l'a publiée est modéré ; les administrateurs continuent de tout voir. La règle est implémentée dans jobs.controller.ts :

apps/backend/src/controllers/jobs.controller.ts
function isPubliclyVisible(job: JobWithPoster): boolean
{
    if (job.company !== null && isModerated(job.company)) {
        return false;
    }
    if (job.poster !== null && isModerated(job.poster)) {
        return false;
    }
    return true;
}

Migrations

Le schéma TypeScript est la source de vérité ; le SQL est généré, jamais écrit à la main. Sept migrations sont présentes, journalisées dans drizzle/meta/_journal.json.

depuis la racine du dépôtshell
# 1. écrire la table dans src/db/schema.ts, puis :
pnpm --filter backend db:generate   # crée drizzle/00XX_nom.sql + le snapshot
pnpm --filter backend db:migrate    # applique les migrations en attente
pnpm --filter backend db:studio     # inspecteur graphique de la base
En conteneur

Le backend exécute node src/db/migrate.ts && node src/db/seed.ts à chaque démarrage. Une migration commitée est donc appliquée automatiquement chez les autres — mais le fichier SQL doit être commité, pas seulement le schéma.

Maintenance quotidienne

src/cron.ts planifie runDailyMaintenance() à minuit, fuseau Europe/Paris : archivage des offres de plus de 30 jours dans jobs_archive (transaction, compétences comprises, puis suppression de l'originale), purge des archives de plus de 2 ans, et suppression des comptes sans connexion depuis 2 ans.

Authentification et rôles

Better Auth gère les comptes des deux côtés. Le backend le monte en amont de express.json() — le handler lit le corps lui-même — et le frontend consomme la même session via authClient.

apps/backend/src/app.ts
app.all("/api/auth/{*splat}", toNodeHandler(auth)); // AVANT express.json()

app.use(express.json());
app.use("/api-docs", swaggerUi.serve, swaggerUi.setup(swaggerSpec));
app.use("/api", router);
app.use(errorHandler); // toujours en dernier

Les trois rangs

rankRôlePeut
0AdministrateurTout voir, y compris le contenu modéré ; suspendre, bannir, changer un rang, traiter les signalements. Attribué à la main.
1EmployeurGérer son entreprise (companies_id), publier des offres, consulter et traiter les candidatures reçues.
2CandidatValeur par défaut. Profil, compétences, expériences, disponibilités, candidatures, signalements.

Le contrôle d'accès se fait à deux niveaux. requireAuth ouvre la porte ; le contrôle fin appartient au controller, en général via une garde locale du type checkCompanyAccess() qui laisse passer le rang 0 puis compare user.companiesId à l'entreprise visée. Le middleware requireRank(...rangs) existe pour les cas simples et se place après requireAuth.

Session

  • Durée 3 jours, prolongée au bout d'un jour d'usage ; cache cookie de 5 minutes.
  • Un hook databaseHooks.session.create.after met à jour users.last_login_at — c'est cette colonne que lit la purge des comptes inactifs.
  • E-mail de vérification envoyé à l'inscription, valide 1 heure. Sans SMTP_HOST, le lien est simplement écrit dans les logs du backend.
  • emailAndPassword.requireEmailVerification est à false : un compte non vérifié peut se connecter.
Côté navigateur

Le cookie de session est envoyé par le navigateur, pas par un en-tête Authorization. Tout appel authentifié depuis lib/api.ts doit porter credentials: "include", et l'origine du front doit figurer dans FRONTEND_URL (CORS + trustedOrigins). Un 401 inexpliqué vient presque toujours de l'un de ces deux points.

Format des corps

L'API reçoit du snake_case (companies_id, salary_min, max_applicants) et renvoie du camelCase, tel que Drizzle le produit. La conversion se fait dans le controller, champ par champ — c'est volontaire, et c'est ce qui permet à PATCH de distinguer « champ absent » de « champ mis à null ».

Recette — ajouter une table

Exemple suivi dans les trois recettes suivantes : des favoris, permettant à un candidat de mettre une offre de côté. Une table de jonction, une contrainte d'unicité, deux clés étrangères en cascade.

  1. Déclarer la table dans le schéma

    Tout se passe dans schema.ts. Les colonnes reçoivent leur nom SQL en argument ; les contraintes de table vont dans le tableau retourné par le troisième paramètre.

    apps/backend/src/db/schema.tsajout
    export const favorites = pgTable(
    "favorites",
    {
        id: serial("id").primaryKey(),
        userId: integer("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
        jobId: integer("job_id").notNull().references(() => jobs.id, { onDelete: "cascade" }),
        createdAt: timestamp("created_at").defaultNow(),
    },
    (t) => [unique().on(t.userId, t.jobId)] // un favori par couple candidat/offre
);

  2. Déclarer les relations

    Sans bloc relations, l'option with: de db.query ne saura pas joindre. Il faut aussi ajouter le many() réciproque dans les relations existantes de users et jobs.

    apps/backend/src/db/schema.tsajout
    export const favoritesRelations = relations(favorites, ({ one }) => ({
    user: one(users, { fields: [favorites.userId], references: [users.id] }),
    job: one(jobs, { fields: [favorites.jobId], references: [jobs.id] }),
}));

// dans usersRelations : ajouter   favorites: many(favorites),
// dans jobsRelations  : ajouter   favorites: many(favorites),

  3. Générer puis appliquer la migration

    db:generate compare le schéma au dernier snapshot et écrit un fichier SQL numéroté. Relisez-le : c'est là qu'on repère une colonne oubliée ou un NOT NULL ajouté sur une table déjà remplie.

    racine du dépôtshell
    pnpm --filter backend db:generate
# → apps/backend/drizzle/0007_xxx.sql + drizzle/meta/0007_snapshot.json

pnpm --filter backend db:migrate
# en conteneur, migrate.ts tourne déjà au démarrage du service backend

  4. Commiter le SQL avec le schéma

    Le fichier drizzle/00XX_*.sql, le snapshot et drizzle/meta/_journal.json font partie du changement. Sans eux, la base des autres ne bougera pas.

Ne jamais faire

Modifier un fichier de migration déjà appliqué, ou renommer une migration existante. Le journal se désynchronise et db:migrate rejoue ou saute des étapes. Une correction se fait toujours par une nouvelle migration.

Recette — ajouter une route et son controller

Cinq fichiers touchés, toujours les mêmes, toujours dans cet ordre. On expose ici /api/favorites.

  1. Le schéma de validation

    Un fichier par ressource, deux exports par verbe qui écrit. Le patch se dérive du post avec .partial().

    apps/backend/src/schemas/favorites.schema.tsnouveau
    import {z} from "zod";

export const postFavoriteSchema = z.object({
    job_id: z.number().int(), // l'API reçoit du snake_case
});

  2. Le controller

    Une fonction exportée par endpoint, signature Express complète, next() en fin de fonction comme partout ailleurs dans le projet. On récupère l'utilisateur par getCurrentUser, on valide, on vérifie l'existence, puis on écrit.

    apps/backend/src/controllers/favorites.controller.tsnouveau
    import {Request, Response, NextFunction} from "express";
import {validateJson} from "../utils/validateJson.utils.ts";
import {getCurrentUser} from "../utils/currentUser.utils.ts";
import {isUniqueViolation} from "../utils/dbError.utils.ts";
import {HttpError} from "../types/httpError.ts";
import * as schemas from "../schemas/favorites.schema.ts";
import {db} from "../db/index.ts";
import {favorites, jobs} from "../db/schema.ts";
import {and, eq} from "drizzle-orm";

export async function getFavorites(req: Request, res: Response, next: NextFunction)
{
    const user = await getCurrentUser(req);

    const rows = await db.query.favorites.findMany({
        where: eq(favorites.userId, user.id),
        with: { job: { with: { company: true, address: true } } },
    });

    res.json(rows);

    next();
}

export async function postFavorite(req: Request, res: Response, next: NextFunction)
{
    const user = await getCurrentUser(req);

    if (!validateJson(schemas.postFavoriteSchema, req, res)) {
        return; // validateJson a déjà répondu 400
    }

    const job = await db.query.jobs.findFirst({ where: eq(jobs.id, req.body.job_id) });
    if (!job) {
        throw new HttpError(404, "Offre introuvable");
    }

    let created;
    try {
        const rows = await db.insert(favorites).values({
            userId: user.id,
            jobId: req.body.job_id,
        }).returning();
        created = rows[0];
    } catch (error) {
        if (isUniqueViolation(error)) {
            throw new HttpError(409, "Cette offre est déjà dans vos favoris");
        }
        throw error;
    }

    res.status(201).json(created);

    next();
}

export async function deleteFavorite(req: Request, res: Response, next: NextFunction)
{
    const user = await getCurrentUser(req);

    const id = Number(req.params.id);
    if (isNaN(id)) {
        throw new HttpError(400, "Identifiant de favori invalide");
    }

    // le filtre sur userId fait office de contrôle de propriété
    const rows = await db.delete(favorites)
        .where(and(eq(favorites.id, id), eq(favorites.userId, user.id)))
        .returning();
    if (rows.length === 0) {
        throw new HttpError(404, "Favori introuvable");
    }

    res.json({ deleted: rows[0].id });

    next();
}

  3. Le fichier de routes

    Rien d'autre que le câblage et la documentation OpenAPI. Le bloc @openapi alimente /api-docs : les chemins s'y écrivent sans le préfixe /api, déjà déclaré comme serveur dans swagger.config.ts.

    apps/backend/src/routes/favorites.routes.tsnouveau
    import {Router} from "express";
import {requireAuth} from "../middlewares/requireAuth.middleware.ts";

const router = Router();

/**
 * @openapi
 * /favorites:

 *       - bearerAuth: []

 *       200:

 *       401:
 *         description: Missing or invalid session
 */

/**
 * @openapi
 * /favorites:
 *   post:
 *     summary: Save a job
 *     tags: [Favorites]

 *       - bearerAuth: []
 *     requestBody:
 *       required: true
 *       content:
 *         application/json:
 *           schema:
 *             type: object
 *             required: [job_id]
 *             properties:
 *               job_id: { type: integer }
 *     responses:
 *       201:

 *       409:

 */
router.post("/", requireAuth, favoritesController.postFavorite);

/**
 * @openapi
 * /favorites/{id}:

export default router;

Nommage des chemins

Sous Express 5, les segments génériques s'écrivent {*splat} et non plus * — c'est la forme utilisée pour Better Auth dans app.ts. Une route /:id doit toujours être déclarée après les chemins littéraux qui pourraient s'y confondre (/received, /siret/:siret).

Recette — brancher le frontend

Le front ne parle à l'API qu'à travers lib/api.ts. Un composant qui appelle fetch lui-même est un bug de conception : la base d'URL, la gestion d'erreur et le typage s'y perdent.

  1. Ajouter le type et les appels

    Une fonction par endpoint. Convention du fichier : jamais d'exception vers l'appelant — un échec réseau rend une valeur vide, un échec HTTP rend le message d'erreur de l'API via errorMessage().

    apps/frontend/lib/api.tsajout
    export type Favorite = {
    id: number;
    createdAt: string | null;
    job: ApiJob;
};

export async function fetchFavorites(): Promise<Favorite[]> {
    let response;
    try {
        response = await fetch(API_URL + "/api/favorites", {
            credentials: "include", // indispensable : la session est un cookie
            cache: "no-store",
        });
    } catch {
        return [];
    }

    if (!response.ok) {
        return [];
    }

    return (await response.json()) as Favorite[];
}

export async function postFavorite(jobId: number): Promise<string | null> {
    let response;
    try {
        response = await fetch(API_URL + "/api/favorites", {
            method: "POST",
            credentials: "include",
            headers: { "Content-Type": "application/json" },
            body: JSON.stringify({ job_id: jobId }), // snake_case côté API
        });
    } catch {
        return "Le service ne répond pas. Réessayez.";
    }

    if (response.ok) {
        return null; // null = succès
    }

    return await errorMessage(response, "Impossible d'ajouter cette offre aux favoris.");
}

  2. Créer l'écran

    Un dossier sous app/ et un page.tsx suffisent : la route existe. Ici la page a besoin de la session, elle est donc cliente ; une page en lecture seule resterait un composant serveur et appellerait fetchFavorites() directement dans son corps async.

    apps/frontend/app/favoris/page.tsxnouveau
    "use client";

import { useEffect, useState } from "react";
import { authClient } from "@/lib/auth-client";
import { fetchFavorites, toJob, type Favorite } from "@/lib/api";
import JobList from "@/components/job-list";

export default function FavorisPage() {
    const { data: session } = authClient.useSession();
    const [favorites, setFavorites] = useState<Favorite[]>([]);

    useEffect(function () {
        if (!session) {
            return;
        }
        fetchFavorites().then(setFavorites);
    }, [session]);

    if (!session) {
        return <p className="p-8">Connectez-vous pour retrouver vos offres mises de côté.</p>;
    }

    return <JobList jobs={favorites.map(function (f) { return toJob(f.job); })} />;
}

  3. Rendre l'écran atteignable

    Ajouter l'entrée dans components/header.tsx (ou footer.tsx), et un export const metadata si la page est un composant serveur — le template défini dans app/layout.tsx y ajoute automatiquement « — GéoEmploi ».

Piège classique

Une page serveur qui appelle une route authentifiée ne recevra rien : le cookie n'est pas transmis automatiquement par un fetch côté serveur. Tout ce qui dépend de la session se lit côté client, ou en repassant explicitement les en-têtes.

Autres recettes

Ajouter un champ à une table existante

  1. Ajouter la colonne dans schema.ts. Sur une table déjà peuplée, la rendre nullable ou lui donner un .default() — un NOT NULL sans défaut fait échouer la migration.
  2. pnpm --filter backend db:generate, relire le SQL, db:migrate.
  3. Étendre le schéma Zod correspondant (postXSchema ; le patch suit automatiquement via .partial()).
  4. Reporter le champ dans le controller : le bloc values du POST, et un if (req.body.champ !== undefined) dans le PATCH.
  5. Compléter le bloc @openapi de la route, puis le type ApiX et le mapper (toJob, toCompanyPin…) côté front.

Ajouter une primitive d'interface

Les composants components/ui/ viennent de shadcn/ui, configuré par components.json (style « new-york », icônes Lucide, alias @/components et @/lib/utils). Une nouvelle primitive s'ajoute avec la CLI depuis apps/frontend, puis vit dans le dépôt comme n'importe quel fichier — on la modifie librement.

apps/frontendshell
pnpm dlx shadcn@latest add accordion

Les couleurs ne se codent pas en dur : elles passent par les jetons de app/globals.css (--primary, --action, --muted…), déclinés en clair et en sombre, et exposés à Tailwind 4 par le bloc @theme inline. --action-text existe spécifiquement pour garder 4,5:1 de contraste sur du texte, exigence RGAA du projet.

Afficher une nouvelle donnée sur la carte

components/map.tsx ne connaît que des MapPoint — un identifiant, des coordonnées, un titre, un sous-titre, un détail et un libellé lu par les lecteurs d'écran. Pour cartographier autre chose que des offres, il suffit d'écrire un mapper vers ce type, comme toCompanyPin() le fait pour les entreprises. Filtrez toujours en amont sur needsLocationCheck === false : une entité non géocodée n'a pas de coordonnées exploitables.

Ajouter une tâche planifiée

Écrire la fonction dans db/maintenance.ts, l'appeler depuis runDailyMaintenance(). cron.ts n'a pas à changer tant que la fréquence reste quotidienne ; pour un autre rythme, ajouter un cron.schedule() en conservant timezone: "Europe/Paris". Toute opération qui touche plusieurs tables passe par db.transaction(), comme l'archivage des offres.

Conventions et pièges

Style de code

  • Indentation 4 espaces, guillemets doubles, points-virgules.
  • Backend : accolade ouvrante à la ligne pour les déclarations de fonction, imports collés aux accolades (import {db} from …).
  • Frontend : function () {} plutôt que les fonctions fléchées dans les callbacks — c'est la forme employée partout dans components/ et lib/.
  • Conditions explicites : if (value !== undefined && value !== null), pas de if (value) sur un nombre ou une chaîne.
  • Commentaires en français, réservés au « pourquoi ». Les commentaires legacy du schéma signalent des colonnes conservées pour compatibilité mais non exposées.

Ce qui casse le plus souvent

  • Import sans extension .ts dans le backend → module introuvable au démarrage.
  • Import de Leaflet dans un composant serveur → erreur window is not defined. Passer par dynamic(..., { ssr: false }).
  • credentials: "include" oublié → 401 sur une route pourtant ouverte à la session.
  • NEXT_PUBLIC_API_URL absente → next.config.ts lève au démarrage, volontairement, plutôt que de laisser un front muet.
  • Nouvelle table absente de l'export de schema.ts → db.query.maTable n'existe pas ; l'objet schema passé à drizzle() est ce qui peuple db.query.
  • Relation oubliée → with: { … } échoue silencieusement au typage puis à l'exécution.
  • errorHandler déplacé → il doit rester le dernier app.use(), sinon les erreurs remontent brutes.
  • Contrainte d'unicité non interceptée → 500 au lieu du 409 attendu. Enrober l'insertion et tester isUniqueViolation(error).
  • Route /:id déclarée trop tôt → elle capture /received ou /siret/….

Avant d'ouvrir une pull request

  • pnpm typecheck et pnpm lint passent sur les deux apps.
  • Le fichier de migration et son snapshot sont commités avec le schéma.
  • Les blocs @openapi décrivent les nouveaux endpoints, y compris les codes d'erreur.
  • Les nouveaux écrans respectent les jetons de couleur et gardent un contraste conforme au RGAA.
  • Toute donnée personnelle ajoutée est reportée dans docs/rgpd.md, l'export /api/extract et le registre des traitements.

GéoEmploi — monorepo geoemploi. Documents connexes dans docs/ : registre RGPD, AIPD, contrôle RGAA, diagramme de base au format DBML. La référence exécutable de l'API reste /api-docs, générée depuis les fichiers de routes.
